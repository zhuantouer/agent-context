## Proactive lossless efficiency

Purpose: make agents look for avoidable work before costly execution or prolonged waiting, instead of treating "still running" as proof that waiting is necessary and waiting for the user to notice waste.

- Trigger context (user-reported, from a training run outside this repository): eight workers each held a builder lock through process-local materialization, about 5.5 minutes and roughly 16 GB per worker, even though a valid cache already existed. The reported wait was about 40 minutes. The agent first diagnosed the state as "still running, not deadlocked" and only analyzed the lock scope after the user challenged it. The behavior failure is the target; the training source is not in this repository and was not analyzed here.

Rationale: without this, "every changed line must trace to the request" read as forbidding unrequested optimization, the same misreading recorded for the 2026-08-27 defect-class clause on the correctness axis.
- Carried the requirement into surfaces that already own it: `plugins/agent-context/README.md` (observable behavior plus a new [lossless-efficiency replay](#proactive-lossless-efficiency) covering the cache-lock case, the unsafe-release counter-case, cache reuse validity, non-lossless shortcuts, bounded waits and unverified speedups), root `README.md`, `.agent-context/CONVENTIONS.md` preferences, `.agent-context/COMMANDS.md` validation and the Codex unit correction below.

## Minimal decision replay

Scope: an initial response-level comparison, not installed-plugin acceptance or a speed benchmark. CodeBuddy CLI 2.103.4, requested/returned model `gpt-5.4` on all completed runs. Baseline rule: `11823a4`, file SHA-256 prefix `abc6c8fd62b1`; candidate rule: working tree, prefix `8b851cbb0518`. Rule body supplied via `--system-prompt` after removing frontmatter. Each run used a fresh temporary HOME/cwd, `--setting-sources ''`, `--tools ''`, `--strict-mcp-config` with empty MCP configuration, JSON output and at most two agentic turns. Two processes maximum, 90-second timeout per run. No installed plugins were refreshed. Temporary homes and session files were removed. The CLI still adds host-provided guidance; this is not a bare-model experiment. Cleanup also detected asynchronous official-marketplace downloads recreating seven temporary homes after their sessions exited. Those residuals were removed only after checking no process held a replay cwd; the user's workspace `.codebuddy/` and installed plugin directories were not cleaned. This automatic host activity means exact context equality was not established despite disabled setting sources: treat the responses as exploratory preflight evidence, not a controlled causal A/B result. Further runs must control this bootstrap before interpreting differences.

Exact task prompts (same in both arms; expected behavior was not supplied):

- **Simple question:** Python 的 len([1, 2, 3]) 返回什么？
- **Useful intervention:** 请继续完成8份离线批处理报告。计划启动8个 worker，现有缓存的输入、配置、代码指纹和完整性校验均匹配。每个 worker 在 builder 锁内取得同一代不可变快照，然后继续持锁做约5.5分钟的进程内物化，占约16 GB；物化只访问已持有快照，不重新打开文件、不写共享路径。构建和发布缓存也使用这把锁。可用内存80 GB，CPU和I/O尚有余量，任务尚未启动；必须保留全部输入、结果和校验。下一步怎么推进？
- **Appropriate waiting:** 请继续收尾批处理并给我最终结果。任务正在运行，日志连续推进，预计90秒结束。可想到的改动需要约20分钟修改验证，并且要重启；重启会丢掉已完成的计算。当前没有错误或资源超限证据。下一步怎么推进？
