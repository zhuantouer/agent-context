## Layout survey: how popular multi-harness plugins organize their repos

Purpose: the user asked whether this repository's directory structure should be optimized, and how popular plugins (Claude Code, Cursor and friends) organize directories and support multiple IDEs/harnesses. Read-only survey — no repository change. Local sample: `/Users/zishuaizhang/workspace/superpowers` (obra/superpowers, v6.4.1) read from disk; the rest from vendor docs.

Facts (vendor docs):
- Claude Code (code.claude.com/docs/en/plugins-reference): manifest optional at `.claude-plugin/plugin.json`; components must sit at the **plugin root** — `skills/`, `commands/`, `agents/`, `workflows/`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `bin/`, `output-styles/`, `themes/`, `monitors/`, `settings.json`. No `rules/` slot, and "a `CLAUDE.md` at the plugin root is not loaded". Marketplace index is `.claude-plugin/marketplace.json`; a single-plugin repo can use `"source": "./"`. Unrecognized top-level manifest fields are ignored, so one manifest may double as another ecosystem's.
- Cursor (cursor.com/docs/reference/plugins): two formats distinguished by manifest location — Agent Plugins (root `plugin.json`, skills + MCP only) and Cursor plugin (`.cursor-plugin/plugin.json`, full set including `rules/`). Multi-plugin repos put `.cursor-plugin/marketplace.json` at the repo root; entry resolution looks for `<source>/.cursor-plugin/plugin.json`. Without a manifest, Cursor auto-discovers `rules/`, `skills/`, `agents/`, `commands/`, `mcp.json`, `hooks/hooks.json`.
- agent-plugins.org: open standard v1.0.0 (initial TSC: Amazon, Cursor, Microsoft, OpenAI, Vercel). Layout: root `plugin.json` (`$schema` `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`), `skills/`, `mcp.json`, plus reverse-domain extension namespaces (`com.example.client/hooks/`). Cursor loads conforming plugins unmodified. Whether Claude Code loads it is **not** established by anything read today.

Facts (superpowers, read locally): repo root **is** the plugin — `skills/`, `hooks/`, `scripts/`, `tests/`, `docs/`, `assets/`, `README.md`, `RELEASE-NOTES.md`, plus eight per-harness manifests side by side: `.claude-plugin/` (plugin.json + marketplace.json, `source: "./"`), `.codex-plugin/`, `.cursor-plugin/`, `.devin-plugin/`, `.hermes-plugin/` (plugin.yaml), `.kimi-plugin/`, `.muse-plugin/` (plugin.json + marketplace.json), `.agents/plugins/marketplace.json`, `.opencode/plugins/superpowers.js`, `.pi/extensions/superpowers.ts`, plus root `package.json` (declares `pi.extensions`, `pi.skills`, `main` → OpenCode plugin), root `index.js`, `gemini-extension.json` + `GEMINI.md`, `CLAUDE.md`/`AGENTS.md`.
- Per-harness hook configs live in one `hooks/` dir: `hooks.json` (Claude Code default, `${CLAUDE_PLUGIN_ROOT}`, `matcher: startup|clear|compact`) and `hooks-cursor.json` (`version: 1`, lowercase `sessionStart`, relative command, no matcher/type) — deliberately *not* one canonical template. Codex declares `"hooks": {}` **on purpose**, to suppress its `hooks/hooks.json` auto-discovery.
- One extensionless hook script `hooks/session-start` detects the host by env var (`CURSOR_PLUGIN_ROOT` / `CLAUDE_PLUGIN_ROOT` + not `COPILOT_CLI` / `MUSE_PLUGIN_ROOT`) and emits one of three JSON shapes; the comment records that Claude Code reads both `additional_context` and `hookSpecificOutput` without dedup, so emitting both double-injects. `hooks/run-hook.cmd` is a batch/sh polyglot for Windows.
- Two invariants stated as project law: skills name **actions**, never tool names (per-harness tool mapping lives in `skills/using-superpowers/references/<harness>-tools.md`); and everything ships through the harness's own install mechanism — never edit the user's global/personal config.
- Version lockstep: `.version-bump.json` lists every manifest path + field, `scripts/bump-version.sh` keeps them in sync; a new manifest not registered there ships stale.
- Distribution: `scripts/sync-to-codex-plugin.sh` rsyncs into an external fork with an anchored EXCLUDES list that drops repo-internal dirs **and the other harnesses' dotdirs** (`.claude-plugin/`, `.cursor-plugin/`, `.devin-plugin/`, `.kimi-plugin/`, `.opencode/`, `.pi/`, `/docs/`, `/scripts/`, `/tests/` …).
- New-harness SOP is a written doc, `docs/porting-to-a-new-harness.md`, with three integration shapes (A shell-hook, B in-process plugin, C instructions-file), a capability checklist, and a mandatory live acceptance test.

Comparison with this repository:
- **Matches**: three `.<host>-plugin/` manifests side by side over one shared content tree; one shared hook implementation with per-host hook configs; skills kept host-neutral; a validator that enforces manifest/version consistency (their role = superpowers' `.version-bump.json` + bump script).
- **Differs**: content sits under `plugin/` instead of the repo root. Every sample with marketplace or git-URL installs puts the plugin at the root, because `source: "./"`, `gemini extensions install`, `kimi /plugins install`, `opencode` `plugin` git URLs and Cursor marketplace entries all resolve a plugin **directory** from the repo root. Our `plugin/` nesting therefore blocks every install path except our own copy-based installer.
- **Differs**: no per-harness exclusion list — `copy_plugin` ships all three dotdirs to every host (the Cursor install carries `.codex-plugin/`). Harmless today, but it is the drift superpowers excludes explicitly.
- **Differs**: no root `plugin.json` in the Agent Plugins format, which is the one standard Cursor loads natively and whose whole point is one package for many clients.
- **Differs**: no written per-harness porting SOP and no `tests/<host>/` split; harness knowledge lives in `hook_payload.py` + `ARCHITECTURE.md`.

Conclusion: the shape is right, the depth is the open question. Flattening `plugin/` to the root is the industry norm but only pays off when something installs from the repo — and distribution was deliberately dropped earlier today, so the concrete benefit right now is zero while the cost is real (the copy installer would need an include/exclude list to keep `.agent-context/`, `scripts/` and `.git` out of the installed package). Recommendation given to the user: keep the current depth until distribution returns; do the four no-regret moves first (root Agent-Plugins `plugin.json`, per-harness exclusion list, bump script driven by a manifest list, per-harness porting doc). Assumption, unverified: CodeBuddy's manifest schema has no public reference implementation in these samples — superpowers covers Claude Code, Codex, Cursor, Copilot, Gemini, Kimi, OpenCode, pi, Devin, Muse, Hermes, Antigravity but not CodeBuddy, so any CodeBuddy-specific claim stays untested.
